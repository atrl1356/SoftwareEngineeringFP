# Design

## Context

儲存庫已有開發規則與第 1–42 題決策，本次是第一個產品 change，沒有待遷移的產品資料或既有 API。教師自己的 Google Sheets 兼具匯入來源及回寫目的地；同一分頁可能跨場重用。本機課堂驗收需要三個獨立身分並可重啟後端。

## Goals / Non-Goals

本設計保證三個邊界可分別驗收：一筆送答何時取得順位、哪個角色何時取得勝答、一題何時能認列為寫入完成。第一輪使用單一 Node.js 收件程序及持久化 SQLite 檔案；跨節點排序、第二輪題組、CSV 與公平順位不在本次部署範圍。

## Decisions

### 1. 角色頁面與伺服器授權

Vue 3、TypeScript、HTML 與 CSS 提供教師頁及學生頁。前端共用題號與階段型別；Fastify 依已驗證的工作階段建立不同回應。學生回應從允許清單組裝，不序列化教師監看物件。開放時本組收據只提供本組的答案與狀態，不含全場流水號。教師操作另核對活動擁有者。

教師使用預先配置的帳號與密碼雜湊，登入成功後取得伺服器核發的工作階段；Google 工作表授權獨立處理，規劃由教師授權後端存取其試算表，憑證只在後端使用。學生活動加入碼查找場次；建組在交易中依該場建組順序配置公開代號，隨機組內碼遇撞碼則重取。組員身分綁定到場次及組別，由後端驗證；工作階段失效時以組內碼重新加入。準備中與開放中均可建組，以（活動、組長學號）唯一約束處理重複請求。已驗證的原組長重送回覆原代號；單憑他人學號不能取得既有組憑證。開放中新組交易成功即增加教師監看的總組數；晚到組員以組內碼加入既有組，代號與組數不變。結束後可憑原組內碼恢復結果檢視，不能新增組別或送答。公開代號不作入組憑證。

### 2. 同一收件入口裁決開場、送答與截止

單一 Node.js 程序為開場、送答、截止設置共同的 HTTP 收件入口。在 Fastify 解析本文與啟動非同步驗證之前，同步掛接原始請求串流的完成通知，讓原本的解析器正常消費本文。本文收齊（無本文則請求完整結束）時立即登記佇列位置；分段請求不能於收到首段時占位，完整前中斷的請求也不占位。不得以 preValidation、preHandler、handler 的進入時間或解析回呼完成順序取號。解析或授權稍後完成時，將成功或拒絕結果交回原位置；佇列依序處理，拒絕、解析失敗及取消均須釋放已登記的位置。讀查詢及 Sheets 網路 I/O 不占用裁決佇列。

每筆完整命令依入列順序取得唯一遞增收件序；SQLite 保存已處理的序號上限，重啟從已提交的上限之後繼續。無效及重送事件不增加有效順位，收件序可有間隔。驗證失敗須讓下一筆繼續。接受有效新答時於同一短交易核對身分、場次、階段及資格，配置該題有效順位並插入原文、收件序與順位。提交成功才回覆收據。開場命令輪到時才查權限與已確認匯入版本，成功則交易切換階段。輪到較早送答時仍在準備中就拒收，即使後方有效開場命令已通過驗證。截止交易依同一順序鎖定活動並保存每題最早有效提交的參照或無勝組結果，再回覆教師成功。用戶端先按、網路先連線或 SQLite 寫得快都不改判。

### 3. 資料與重啟復原

| SQLite 資料 | 必要欄位與約束 |
|---|---|
| 教師、活動與小組 | 教師帳密雜湊、活動擁有者、階段、活動碼；組別從屬活動，組長學號、場內唯一公開代號與組內碼。 |
| 匯入版本與題目 | 保存最近成功版本與目前是否可開場，記錄 spreadsheetId、sheetId、原可見題號、正規化題號、題序、題目特徵及兩個原目標範圍。開場後鎖定。 |
| 有效提交 | 場次、組別、題目、LF 原文、收件序、題內順位；唯一鍵 (場次, 組別, 題目) 與 (場次, 題目, 順位)，跨場參照以外鍵限制。 |
| 題目結果與回寫 | 唯一的場次／題目結果，勝出提交參照或無勝組、公布時間、回寫進度、預期雙格字串、預覽目標位置與合併範圍、兩格的原值／型別、教師核可的覆蓋內容、目標最後寫入版本及嘗試結果。 |

同身分重送先辨認同題的既有收件：相同原文回原收據，開放中異文回「已提交」；截止後只允許重查已受理內容，拒收新答。唯一鍵是雙裝置的最後保障，遇重複鍵讀回首筆，不使用覆寫式插入。後端退出前未提交的交易由 SQLite 回滾；重啟以持久資料重建讀模型，恢復待處理或結果未知的寫入，先對帳再續作。關頁後不要求還原未送草稿。

### 4. 短輪詢與公布狀態

學生頁約每秒取得含當前活動階段與本組狀態的快照，避免舊回應覆蓋新階段，可使用單一進行中請求與本地請求世代。加入、重連或切換場次先停用輸入，收到當前快照再啟用。班級開場、截止各自以教師成功回應到已開啟學生頁呈現為計時區間，於正常本機連線獨立驗證 2 秒上限。

| 事件 | 勝組 | 學生可取得的系統勝答 | 教師可見的外部寫入進度 |
|---|---|---|---|
| 開放中 | 教師看暫時順位 | 尚未公布 | 尚不可確認 |
| 整場截止 | 每題固定並公開代號，或顯示無勝組 | 尚未公布；本組原收據仍可查 | 有勝組待預覽，無勝組略過 |
| 教師只預覽 | 已固定 | 尚未公布 | 檢查兩格與原值 |
| 教師有效確認該題 | 已固定 | 即可看該題勝答 | 待寫入；後續可為衝突、失敗或完成 |

確認時在分頁序列內重新定位、讀回兩格，核對教師、題目、目標版本、原值、型別及已同意的逐格覆蓋。預覽過期就拒絕本次確認並回傳最新預覽：未公布題仍只顯示勝組，兩格均不寫。核對通過後才在本地交易中一併記錄公布時間與待寫入工作。由後端在交易提交後寫 Sheets；重複確認使用同一活動及題目的工作紀錄。工作程序中斷後依下述跨場規則恢復。若確認後查出新衝突或寫入失敗，仍保留已公布結果。這樣即使 Google 服務暫時離線，學生也可以看到教師已確認公布的內容。

### 5. 匯入、定位、雙格寫入與對帳

後端 TypeScript 的 Sheets 介面支援列出分頁、讀取內容型別與合併範圍、檢查已知權限及寫入指定格。讀表解析及寫入前使用同一套規則：修整表頭，規整題號並保留原標示，找出唯一表格，以試算表／分頁穩定識別碼、原題號與題目特徵定位當前列，分別找兩個表頭所指的儲存格。每個合併區取左上格，兩目標須可區別。若試算表名稱或欄位置改變，顯示當前位置；刪題、替換內容、定位歧義則停止該題。

第一輪以 (spreadsheetId, sheetId) 為序列化範圍。跨場在同一分頁的確認核對、寫入與重試使用同一執行序列；即使只重疊一格或移欄後才產生重疊，亦不會同時從同一份舊值作出覆蓋決定。不同題目也依序進入該頁的寫前核對、批次寫入與對帳區段；等待人工重新確認時釋放分頁。

SQLite 依實際目標位置記錄最近寫入工作的識別碼與遞增版本；預覽保存兩格對應的版本。發送外部請求前先持久記錄此次嘗試與兩個目標，讀回後更新嘗試結果。逾時或重啟留下的結果未知嘗試須先對帳；不可把未知當作可平行重送的許可。後來場次改寫任一重疊格後，即使顯示文字相同，舊工作也須以新版本重新取得教師同意。版本只追蹤本系統的寫入；人工共編以實際讀回的原值、型別與位置檢查。

預覽逐格記錄位置、實際內容與預期字串。執行前重讀並核對；目標位置或待覆蓋原值與已確認版本不符時，交還教師核對。空格可填，相同字串免寫，任何公式（包括顯示空白或等於勝答）與不同值都須逐格同意。使用 Sheets 的 `spreadsheets.batchUpdate`，只對當前需更新且已確認的格子發出設定 `userEnteredValue.stringValue` 的請求，欄位遮罩限於值；同批內的更新一起套用，兩格不相鄰也不更新中間格。驗收比對整格格式（如底色、框線、數字格式）、合併範圍及非目標格。Google Sheets 替換值可清除目標舊文字的部分加粗或內嵌連結，本輪不保證這些局部富文字。完成後讀回兩格的實際型別及原文，再持久標記完成。

逾時可能代表 Google 已收到請求。每次重試先於同一分頁序列內重新定位、讀回兩格實際原值與型別，再核對各自的覆蓋同意及寫入版本。若另一場已改寫，先列衝突，保留該場兩格，待教師重新確認。其餘情況，兩格皆符合可直接結案；一格符合且另一格仍是核可的空格時只補空格。新出現的空白、異值、公式或移位均不能套用不相符的舊同意。權限被撤回或無法讀回時保留失敗或待核實狀態。無勝組不建立寫入工作。

### 6. 驗收與團隊分工

Vitest 對可控完整收件事件、SQLite 實體暫存資料檔與可注入失敗的 Sheets 介面測試。以 Vitest 啟動實際監聽本機連接埠的 Fastify 服務，用兩條獨立 HTTP 連線分段傳送本文。第一條先送首段，第二條先送完；由伺服器的完整收件通知同步測試步驟，再送完第一條。以可控閘門延後較早完整請求的驗證，待較晚請求完整抵達後才放行。交換開場／送答、送答／截止及兩組送答的完成順序，每次用新場次核對有效筆數、順位與勝組。另測無本文的控制請求。直接呼叫 handler 或 Fastify inject 可測業務規則，串流順序須以實際連線驗收。重啟案例關閉再開資料庫。Sheets 測試比對兩格型別、原文、其餘格及合併範圍，涵蓋已寫入但回應遺失。測試以固定版本的四欄範本與各案例清單為起點；第 3.2 項列明變體及預期結果。日常 Playwright 使用可重置的 Sheets 替身，第 6.4 項使用有授權的專用 Google 副本。每個案例執行前還原同版快照（值、型別、整格格式、富文字、合併、權限與保護範圍），建立乾淨資料庫及獨立場次；實表由唯讀母版重新複製並套用、核對測試帳號權限。重跑第 37 題應有相同起始資料。

Playwright 使用教師、甲、乙各自獨立的瀏覽器工作階段，在本機啟動前後端，檢查 DOM 與學生實收 API 欄位；第 37 題每一步等候收據再執行下一步，截止與確認之間留出可觀察的檢查點。開場及截止的計時採同一測試程序時鐘並分開斷言，避免用固定睡眠冒充延遲檢查。

## Risks / Trade-offs

- **多程序會失去單一收件順序。** 第一輪以一個收件程序部署，持久化交易短小；若日後多實例需重新設計共同排序。
- **Sheets 與 SQLite 無法共用交易。** 公布與待寫工作先在本地持久化，外部結果靠雙格讀回，避免將網路逾時誤判為成功或未寫。
- **共同編輯可能發生在最後一次讀取與寫入之間。** 預覽版本、寫前核對與寫後讀回可偵測已觀察到的差異；Sheets 批次寫入不提供依兩格舊值比較再交換的保證。實表驗收使用副本，將手動變更插在預覽後或重試前以重現衝突。
- **瀏覽器排程及慢網路影響輪詢延遲。** 分別記錄正常本機的兩次延遲；斷線時停用送答並於重連後取最新快照。

## Migration Plan

首次部署建立空的 SQLite 資料庫與教師帳號，提供教師 Google 授權設定，以預加勝組欄的範本副本驗證匯入及逐題回寫後再供課堂使用。回退時停止新開場並保留資料檔及待核實寫入；恢復同一資料檔後讀回兩格再續作，以免重複寫入原表。
