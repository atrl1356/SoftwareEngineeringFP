# Design

## Context

`server/app.ts` 從工作階段取得教師，列表依 `activities.owner` 篩選。`server/quiz.ts` 已把開場、送答、截止交給同一個 HTTP 完整收件序列，但開場只查匯入狀態，建組只檢查學號非空。收據路由直接查提交，同文重送也會在讀取活動階段前回覆原答案。`client/Student.vue` 在網路或伺服器錯誤後仍會排定下一次輪詢。

`server/db.ts` 已啟用外鍵並提供短交易。`server/writeback.ts` 以試算表及分頁排程工作，`questions.progress` 的「待寫入」同時用於尚未確認及已確認待送兩種情況。`marks` 保存各範圍最後寫入者與版本，另一場也可能使用它。規則來源見 [範圍與決策](proposal.md)。

## Goals / Non-Goals

在現有單一 Fastify 程序下，讓每次移除、還原與清除有可觀察的生效點，區分場次階段、學生存取資格及雲端工作進度。教師以原有課堂管道交付加入碼。跨節點佇列、外部通知服務及工作表資料清除均在本次範圍之外。

## Decisions

### 1. 用獨立欄位記錄移除，逐場提交批次

在活動保存可空的移除時間與單調遞增的生命週期版本。原有活動預設可用，原階段及所有關聯保留。「我的活動」只讀自己的可用列，「已移除」只讀自己的未到期移除列。這使還原可沿用原階段，也避免把移除混進開場／截止狀態機。

單列與批次共用同一條規則。教師核對清單時帶回活動 ID、版本、名稱、碼、階段、資格及阻擋原因。單列與批次確認皆只能提交畫面列為可移除的選取項。後端從教師工作階段取擁有者，去除重複 ID，在每場的 SQLite 寫交易中重讀資格、更新移除狀態、遞增版本並撤銷本場學生身分。準備中可顯示受影響的組數。對不可見 ID 統一回覆無法操作，不揭露其是否存在。每場分別提交，混選的逐場結果可供重新整理及重試。

以教師、活動、操作識別及預期版本辨認同一次操作，將移除／還原及其已提交結果一併記錄。回覆遺失時可重取結果。若當前版本已往後推進，只回覆已處理與當前狀態，不能重播舊移除、重新換碼或發出過時憑證。每次新選取使用新操作識別。這也處理後端在整批送完回覆前中斷的情況。

### 2. 讓移除資格與回寫登記互斥

準備中核對可用狀態。開放中回覆須先截止。已結束在同一交易核對每題：有勝組須已核實兩格寫入，無勝組須為「略過」。另核對該場排隊與執行中的回寫。檢查使用已保存的結案紀錄，毋須向 Google 重新讀表。截止交易已決定勝組及無勝組題的略過狀態。

沿用既有分頁佇列，在確認或重試排入等待之前，用短交易核對場次版本，登記活動、題號、操作及工作狀態（排隊或執行中）。移除與工作登記以 SQLite 寫交易決定先後。登記先完成則阻擋移除，移除先完成則拒絕舊工作。出佇列、送出寫入前及保存結果時再次核對版本。等待網路不持有 SQLite 交易。唯讀預覽及匯入的遲到回應也必須核對版本才能保存。匯入同時檢查原有 `import_revision`，避免移除後迅速還原回準備中讓舊讀取生效。

完成或已知失敗時，一起保存逐題進度及工作結束狀態。服務啟動時，未到有效確認的中斷工作失效，仍未結案的勝組題繼續阻擋移除。已公布且有同意的中斷工作依原雙格規則對帳，僅處理仍可用且版本一致的活動。若遠端可能已寫，先讀回兩格再判斷。保留失敗與衝突供教師重試。已結案的過時請求不重啟寫入。這可處理記憶體中的分頁佇列在重啟時消失的情況。

### 3. 分開驗證管理、學生讀取與原收據

在建場後的活動查詢、活動碼進場、建組、監看、開關場、收據、送答、匯入、重選及逐題寫表入口共用場次存取判斷。移除與還原管理另走原教師權限。收據查詢與同文重送先查當前活動及工作階段，再辨認原收據。一般已結束且可進入的場次仍可憑有效身分查本組收據與已公布結果。

學生舊頁使用可由程式辨認的「本場無法使用」回覆。已移除、已到期或本場撤銷的學生身分均不能因重新輪詢取回資料。服務可保留已撤銷的本場工作階段標記至清理，以辨認撤銷，不得當作有效憑證。舊憑證到期或清除後也能返回加入入口。前端清除本場憑證、快照與草稿，取消計時器，忽略早於終止狀態的成功回覆及送答回呼。暫時的網路錯誤仍可重連。教師與其他場次的工作階段各自保留。

### 4. 依原場次階段還原憑證

| 原階段 | 還原交易及後續入口 |
| --- | --- |
| 準備中 | 以相同場次與組別 ID 換發新活動碼與每一組新碼，排除碰撞及該場已撤銷的碼。原教師可再次查看當次有效新碼與對應公開代號，分別交給各組長。學生拿新活動碼及自己組的新碼重新加入。 |
| 已結束 | 移除期間保留原活動碼與每組原碼但停用查找，保留活動碼的唯一性。還原後重新開放原碼查找，要求重新進場取得新工作階段並用原組碼加入。沿用第 28 題的欄位篩選，不提供他組私人收據、完整順位、新建組或送新答。 |

兩種還原都在同一交易內核對原教師、移除版本與期限，更新可用狀態及版本，並保留舊身分的撤銷狀態。準備中的所有碼一次換發，碰撞重試不會留下半張名冊的新碼。加入碼只透過授權入口顯示，不放入公開結果、Sheets 或操作日誌。新碼分發與已結束場沿用原碼，是本次提案對第 46、49 題兩個待決點的確認結果。

### 5. 到期清理與資料邊界

使用伺服器持久化的移除時刻，期限是該時刻加 240 小時。還原交易取得寫鎖後取當下時刻，嚴格小於期限才可還原。清理在服務啟動及運行期間定時掃描到期活動，逐場開短交易，再次核對移除版本與到期條件。即使掃描尚未執行，到期的活動也不再接受還原。可注入時鐘及一次掃描入口以重現截止邊界。

保持外鍵有效，依關聯移除本場學生工作階段、提交、工作與操作紀錄、逐題結果及對照、組別與碼，再移除活動。任一步失敗就回滾整場，下次可重試。保留 `teachers`、教師與 OAuth 工作階段、共用表及 `inbox` 的全域收件序。`marks` 跨場共用，保留判斷範圍重疊所需的最後寫入識別與版本。清理不對 Google 發出寫入，也不透過工作表原值反推該場歷史資料。

### 6. 新建組及零組開場

在前後端以字串處理學號，去首尾空白後須整串符合 `^1[0-9]{8}$`。學生輸入欄使用文字及數字鍵盤提示，避免數字欄位轉型或全形轉換。後端只在建立新組前套用格式。舊組的身分核對及組內碼加入沿用既有驗證，不改舊學號。新組配置代號與人數更新仍在原交易內。

沿用既有有序開場路由。在輪到開場命令時核對教師、可用版本、階段、有效匯入，再查 `groups_` 的實際組數。零組首次請求只回覆確認提示，附與教師、場次、生命週期及匯入版本綁定的確認憑據，釋放收件序列。取消無狀態轉換。教師確認是另一個完整請求，重新驗證後正式開場。此時即使已有組別成立，仍可開場。已開放時重送回覆當前階段，已結束不得重開。首個請求若已有組別，一次完成開場。與移除競爭時以生效交易判斷，正式開場、送答、截止之間仍依既有完整收件序裁決。

## Risks / Trade-offs

- 同一張表可能在 A 完成後被 B 變更。保留重疊範圍版本，並以 Sheets 替身確認移除、還原與清除共新增零次寫入。
- 只用「活動已結束」或「已公布」會誤放行尚未完成的工作。測試分別停住排隊、已送出待回覆、失敗及重啟後待核實的階段。
- 部署舊版服務可能繞過移除標記。切換及回退時保持單一寫入程序，避免兩個版本同時服務同一資料庫。

## Migration Plan

先停收新寫入，取得 SQLite 一致性備份（含尚在 WAL 中的交易），在舊資料副本驗證新增欄位、索引及工作紀錄。舊場均預設可用，舊碼、組長學號、已公布結果與回寫進度依原值遷移。啟動新服務時補清到期場次，再依有效場次對帳回寫。回退前停服務並保留新資料快照，校對切換後的收件及 Sheets 變更。啟用移除後，勿直接以不辨認移除／換碼的舊服務對外提供新資料庫。
